01 / Why we made it

Discovery and operations belong in the same conversation.

Eventure started with a practical question: what would an event platform feel like if the public experience and organizer tools were designed together?

We wanted someone to find a workshop, choose a ticket, use a reward, upload payment proof, and follow the order without losing context. The organizer should be able to run the other side of that journey from one workspace.

03 / The hard part

Checkout is where the product stops being a mock-up.

Seats, vouchers, coupons, and points have to agree—even when an order expires, is cancelled, or gets rejected. Eventure reserves them in one serializable database transaction and restores the same set together when the order changes.

Payment stays grounded in the project’s real flow: customers upload proof, then organizers review it.

04 / How it was built

05 / The collaboration

Built separately.
Designed together.

“The work was divided by journey. The contracts weren’t.”

Eventure was built by two developers in one monorepo. We agreed on the data model and shared API conventions early, owned different product journeys, then brought the work together through reviewed pull requests.
